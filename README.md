# Lilora website

Official Lilora website in ten languages, with English at the site root and
Turkish under `/tr/`. The current content set contains **560 canonical pages:
56 pages in each language**. The existing GitHub Pages deployment serves committed
static files from `main`. `CNAME` stays `lilora.app`; `.nojekyll` stays in place.
The mobile app supports **English and Turkish only**; additional
website languages do not imply additional app languages or public App Store availability.

## Language and route architecture

[`config/languages.json`](config/languages.json) is the authoritative registry for
language codes, display names, HTML/hreflang tags, URL prefixes, Open Graph locales
and browser-language aliases. `scripts/locale-registry.mjs` supplies the generators
and Node checks; `scripts/locale-registry.cjs` supplies the browser-check sources.
The Python content importer reads the same registry. Shared layout embeds its
language options for the browser scripts, so route and language lists are not
maintained independently in each checker or client.

## Edit and verify

The standard build requires Node 22+, Python 3, `npm ci` and an existing Chromium
installation. `playwright-core` does not install Chromium; set `CHROMIUM_PATH` if
needed. Production has no runtime dependency or client framework. An offline
Python asset renderer is available when npm/Chromium rendering cannot run; see
[the promotion asset instructions](assets/brand/README.md#offline-portable-renderer).

1. Home-page copy lives in `pages/home/copy.json`; `scripts/home-promotion.mjs`
   generates all ten home bodies and metadata. Edit other static page bodies in
   `pages/<page>/<lang>.md` (HTML is supported) and their
   localized titles/descriptions in `pages/<page>/meta.json`. Never edit generated HTML.
2. Edit each article independently in `content/articles/<slug>/meta.json` and
   `<lang>.md`. Metadata keeps type (`guide`, `post`, `comparison`), genuine dates,
   sources, image provenance, related slugs and per-language descriptions. Markdown
   starts with one `# Title`; intro is the short answer, `##` creates sections and
   `###` creates subheadings/visible FAQ questions. English/Turkish articles migrated
   with their original slugs, sources, related order and research dates.
3. Plant profiles use `content/plants/<slug>/meta.json` plus `<lang>.md`. Metadata
   requires `slug`, `botanicalName`, `family`, `sources`; each language requires
   `description` and `atAGlance` with `light`, `watering` (check before watering),
   `humidity`, `temperature`, `petSafety` (cats and dogs), `petSafetySource` (primary
   citation URL) and `careLevel`. Body sections include care, visible FAQ and sources.
   The specimen header renders the common name, italic Newsreader botanical name
   and family. No placeholder plant is published. Header library links appear only
   after three real profiles exist in that language.
   Optional `finderLight` (`low`, `medium`, `bright`) feeds the three-question plant
   finder at `plants/finder/` (`scripts/plant-finder.mjs`, `assets/plant-finder.js`):
   one page per language, matched in the browser, no per-answer pages. Pet mode
   shows only `petNonToxic` plants; care and pet lines reuse each profile's `atAGlance`.
4. UI/cookie/recovery strings are in `locales/<lang>.json`; plant filter copy is in
   `content/plants/filters.json`. Supplemental copy for Japanese, Korean, Italian
   and Traditional Chinese is in `locales/<lang>.extras.json`, loaded by
   `scripts/locale-extras.mjs`. Its six groups are `promotion`, `finder`, `handover`,
   `diagram`, `print` and `topicLabels`. Shared HTML is generated by
   `scripts/layout.mjs`; `scripts/build.mjs` assembles pages, hubs, feeds and sitemaps.
   Generated `editorial/{articles,plants,routes}.json` are outputs, not shared editing surfaces.
5. Run `npm run check`, serve with `python3 -m http.server 4173 --bind 127.0.0.1`,
   then execute `scripts/*-check.cjs` with Playwright/Chromium available.
   `scripts/locale-registry.cjs` is a helper, not an executable browser suite.
   Inspect all ten languages, especially CJK text, navigation and legal pages,
   at 320/390/768/1440px. Obtain fresh mobile Lighthouse reports for home, guide and
   support: performance >=90, accessibility/best-practices >=95, SEO 100. Record
   actual reports; syntax checks and manual previews do not establish that a full
   browser or Lighthouse suite passed.
6. Commit sources and generated outputs together. Use one coherent PR; squash only
   after gates pass and the branch is current. Verify Pages and public routes after
   merge. Keep the existing hosting, DNS, app and store configuration.

`AUTO_REDIRECT_ON_FIRST_VISIT = NO`: requested canonical language URLs always win. Browser
preferences can show a dismissible suggestion, never an automatic navigation.
The first supported `navigator.languages` entry is used. Regional Portuguese and
Spanish share their registered prefix; Japanese, Korean and Italian are supported.
`zh-Hant`, `zh-TW`, `zh-HK` and `zh-MO` select Traditional Chinese; explicit
`zh-Hans` preferences do not. Unsupported or missing preferences fall back to English.
Manual choices use local/session storage; session dismissal is separate. Rendered
language links remain free of the `lilora_lang` query marker. A temporary marker is
added only during deliberate click/keyboard/middle-click activation when preference
storage cannot carry the choice into the destination. Existing markers are consumed
without navigation. There is no IP lookup or crawler special case. Native language
links and disclosures work without JS.

Only real article/plant translations receive reciprocal hreflang. HTML and hreflang
tags follow the registry, including `pt-BR` and `zh-Hant`; `x-default` points to the
English counterpart at its root-based path. Sitemap alternates use the XHTML
namespace. Hubs contain complete own-language listings. The blog uses `/blog/`
within each locale prefix; guides and comparisons have their own hubs. A future
incomplete translation must not receive an invented counterpart URL. The multilingual
404 supplies recovery links in all ten languages, has `noindex, follow` and no
canonical or hreflang, and does not move the visitor automatically.

## How the generator works

`npm run build` prepares the code-drawn covers and ten home pages, compiles each
independent article and plant directory with `scripts/import-content.py`, then
renders those records, static pages, tools and hubs through `scripts/build.mjs`
and `scripts/layout.mjs`. Outputs include committed HTML, `editorial/*.json`, ten
language sitemaps, `sitemap.xml`, Atom feeds, reviewed legacy redirects and the
share-card manifest. Finally `scripts/promotion-assets.mjs` creates local QR SVGs,
Playwright-rendered print PDFs and page-specific share cards. Content fingerprints
reuse unchanged renders. GitHub Pages serves the committed files directly and
does not run the asset renderer.

For a constrained environment with the portable renderer's local dependencies
already installed, the equivalent content generation and fallback asset sequence is:

```sh
node scripts/covers.mjs
node scripts/home-promotion.mjs
python3 scripts/import-content.py
node scripts/build.mjs
python3 scripts/promotion-assets-portable.py --review-dir /tmp/lilora-promotion-review
```

The fallback needs current generated content and `assets/brand/share-manifest.json`.
It does not run browser or Lighthouse checks. Its fonts, dependencies, output
contract and preservation limits are documented in
[assets/brand/README.md](assets/brand/README.md). Existing generated assets can be
checked without rewriting them with
`python3 scripts/promotion-assets-portable.py --verify-only`.

To add an article, create `content/articles/<slug>/meta.json` and one Markdown file
per reviewed translation. Use `guide`, `post` or `comparison`; the matching hub and
URL follow the type. Preserve published slugs and genuine research dates. To add a
plant, use the plant metadata fields described above and provide sourced care
summaries and body text. A missing translation receives no invented URL or hreflang.

To add another website language, add its complete definition to
`config/languages.json`, then supply `locales/<lang>.json`, full static/article/plant
bodies and metadata, home copy and plant-filter copy. Supply the six supplemental
copy groups and register their file in `scripts/locale-extras.mjs` when extending
that loader. The shared registry drives generator/importer/checker route lists;
do not add separate hardcoded language arrays to each test or browser script.
Rebuild and check native dropdown links, suggestion/storage behavior, consent,
forms, 404 recovery, reciprocal alternates, feeds, sitemap and promotional assets
before publication. The app's supported languages remain English and Turkish.

## Editorial rules

- Prefer institutional horticultural sources and official product documents.
- Comparisons are desk research, not hands-on testing. Disclose Lilora's interest.
  Do not fabricate ratings, expert credentials, accuracy, absent features or offers.
- A reminder prompts a check, not automatic watering. Do not diagnose from one sign.
- Keep review dates tied to real research or substantive revisions. Do not rotate
  dates or churn pages to simulate freshness. Avoid thin competitor doorway pages.
- Current availability is awaiting App Store review. Use information/support CTAs.
  Do not insert a download badge or App Store destination until the exact public
  listing is verified. Update all affected availability wording after verification.
- Preserve useful source-backed answers. Article and BreadcrumbList metadata match
  visible content. No fabricated Review ratings, FAQ rich-result promises or special
  AI-ranking files. Search inclusion and answer-engine citations are not guaranteed.
- English pages belong at root, Turkish under `/tr/`, and other languages under
  their registry prefixes. Keep reciprocal hreflang only for real counterparts.
  Translate complete bodies; do not place untranslated prose beneath a localized title.
- Use the approved Paper/Ink/Fern/Terracotta palette, Newsreader and system body font.
  No copied competitor graphics or unlicensed photos. Umut’s 20 October 2026
  exception allows generated website atmosphere imagery in natural window light or
  herbarium-style ink, without faces, embedded text, gradients, glow or mascots.
  Logos, app screenshots, icons, diagrams and QR codes are never image-generated.
  Record permitted imagery and its provenance in CREDITS.md.
- All 30 articles and 12 plant profiles have complete counterparts in every
  registered language. Recheck source facts before material updates; localization
  must preserve citations and must not imply a fresh research review.

## SEO rules

Checked by `scripts/seo.test.mjs` (part of `npm test`) and `scripts/a11y-check.cjs`.

- `<title>` is unique and at most 60 characters. The " — Lilora" suffix is added only
  when it fits; a long H1 gets a shorter `seoTitle` in the piece's `meta.json`.
  Meta descriptions are unique and in the page language: 120–155 characters for
  Latin-script locales, 30–110 for Japanese, Korean and Traditional Chinese. The
  registry helpers expose these ranges to metadata and no-JavaScript checks.
- One H1 per page and no skipped heading levels inside `<main>`.
- Canonicals are self-referencing and slash-terminated; no internal links to
  `index.html` or with query strings. hreflang lists only real counterparts, with
  `x-default` pointing at English.
- `sitemap.xml` indexes one `sitemap-<code>.xml` for each of the ten registry
  entries, including `sitemap-en.xml` for English root pages and
  `sitemap-zh-Hant.xml` for `/zh-hant/` pages. Each URL carries its alternates,
  image entries and a `lastmod` from the last git commit that
  touched its sources (files changed but not yet committed use the commit day).
  `robots.txt` points at the index.
- Structured data is limited to `Organization`, `WebSite` (home, no SearchAction),
  `Article`/`BlogPosting` (guides, posts, comparisons, plant profiles; author is the
  Lilora organisation; real published/reviewed dates) and `BreadcrumbList`. No Review,
  Rating, FAQPage, HowTo or MobileApplication markup before launch.
- Every guide, post and comparison links back to its hub and to three related pages;
  every page has at least one inbound internal link.
- One canonical Atom feed per language at its registry prefix plus `feed.xml`,
  linked from every page's `<head>`: English `/feed.xml`, Turkish `/tr/feed.xml`,
  Traditional Chinese `/zh-hant/feed.xml`, and the equivalent paths for the other
  languages. Feeds contain guides and blog posts. Keep the compatibility copy at
  `/en/feed.xml` for existing English subscribers.
- `/.well-known/security.txt` names support@lilora.app; renew its `Expires` date
  before 22 October 2027 (the test fails within a year of expiry being exceeded).
- `lang` attributes must be valid tags; inline English UI labels use `lang="en"`.
- Images over 250 KB appear only as fallbacks behind a WebP `<source>` (press
  downloads link the originals). Newsreader is served as subset WOFF2 (Latin,
  Latin Extended-A incl. Turkish and French) with the WOFF as fallback; the medium
  weight is preloaded and both use `font-display: swap`.
- No on-site search: a static index such as Pagefind would add a build dependency and
  generated bundle for a 560-page site; revisit when the hubs need pagination.

## AI search and agents

AI answer engines read the same public HTML as search engines, so the SEO rules above
are the AI rules too: static pages that need no JavaScript, a short answer at the top
of each guide, dated institutional sources linked inline, accurate structured data and
the sitemap index. Deliberately not done:

- No `llms.txt` or other special AI-ranking file (see Editorial rules). As of
  October 2026 no major AI provider documents reading it, and published server-log
  studies show almost no crawler requests for it.
- `robots.txt` allows every crawler, including AI search/answer bots (OAI-SearchBot,
  ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot, Bingbot) and training
  bots (GPTBot, ClaudeBot, Google-Extended). Blocking training bots would not reduce
  search visibility; that is an owner decision, currently "allow".
- Verified against provider docs on 22 October 2026: OAI-SearchBot (ChatGPT search),
  Claude-SearchBot and PerplexityBot are search crawlers; GPTBot and ClaudeBot collect
  training data; Google-Extended is a robots.txt control token, not a crawler, and does
  not affect Google Search. ChatGPT-User, Claude-User and Perplexity-User fetch pages
  on a user's request, and OpenAI/Perplexity say robots.txt may not apply to them.
- The About page carries the answer-first product fact sheet (what, who, features,
  limits, app languages, availability, contact). Keep it in sync with support/download.
- GitHub Pages also serves repository sources (`/content/`, `/pages/`, `/scripts/`,
  `/locales/`, `/editorial/*.json`, README and package files). `robots.txt` disallows
  only those for every crawler; `scripts/seo.test.mjs` checks that sitemap URLs,
  page assets and ownership files stay crawlable. Canonical pages are indexable;
  `noindex` is limited to the true 404 and reviewed static redirect wrappers.

IndexNow: the key file `/<32-hex key>.txt` at the root lets the site push changed URLs
to Bing (which also supplies ChatGPT search and Copilot), Yandex, Naver, Seznam and
other IndexNow engines. After a content merge is live, run
`node scripts/indexnow.mjs --since YYYY-MM-DD` (or without `--since` for all URLs).
Google does not use IndexNow; it reads `sitemap.xml`.

## Google Analytics and custom cookie preferences

The owner supplied GA4 web measurement ID `G-2CYS6B75ET` on 16 October 2026.
`assets/analytics-config.js` configures that ID. The custom ten-language manager in
`assets/analytics.js` does not load Google or send requests until explicit opt-in.
The initial banner offers equal-weight accept/reject controls and preferences.
The footer always reopens the native modal dialog; keyboard focus is contained,
Escape closes it, and focus returns to its opener. Necessary preference storage is
separate from optional analytics. No marketing category is invented.

Preferences are stored as a versioned object under `lilora.cookie-preferences.v2`
with a choice and timestamp, valid for 180 days. A changed version or expired choice
asks again. A new in-page choice outranks any stale saved grant. Denials also use a tab-scoped
`lilora.cookie-preferences.v2.denied` sessionStorage record, so a read-only
localStorage grant cannot reactivate analytics on same-tab navigation. If neither
store can persist denial, tracking is stopped in place and no automatic reload
occurs; the UI asks the visitor to clear saved site data before leaving/reloading.
All ten languages use the same preference.
Cross-tab withdrawal uses storage events and, where supported, a same-origin
BroadcastChannel for denials even when writes fail. Another tab's grant cannot
overwrite a denial already made in the current document/tab.

Withdrawal sets GA's disable flag, clears the pending queue, removes accessible
owned `_ga` cookies where possible, and reloads without Google only when denial persistence has been verified.
Without durable denial it stays on the current page with GA disabled; a later
explicit re-grant requires recovered persistence and a clean load. It does not claim
to erase data previously processed by the provider. Cookie deletion does not touch
unrelated cookies. All ten website privacy pages document actual behavior; the
mobile app's no-analytics-SDK statement remains explicitly scoped to the app.

Basic consent permits analytics storage only after opt-in and denies ad storage,
ad user data and ad personalization. Google signals and ad personalization are
disabled. URLs omit queries/fragments and referrer text is blank. Manual pageviews
are emitted once per static navigation. Information CTAs use `app_info_click`;
`app_store_click` is reserved for a verified App Store destination, and neither
claims an installation. Cookie lifetime is configured to 180 days without renewal
on each visit. No visitor-provided text is included in custom events.

The GA property dashboard, Enhanced Measurement settings, and server-side retention
were not accessible from this environment. The owner should review those property
settings, including disabling unwanted Enhanced Measurement events. No dashboard
receipt or end-to-end Google collection result is claimed. Visitor-provided contact,
comment and sign-up text is excluded from custom analytics events. Activation tests
intercept Google requests.

Run `node scripts/consent-check.cjs` with Playwright/Chromium available. It tests
initial, reject, accept, reload, revoke, cookies, all ten languages at 320/1440 pixels,
keyboard focus, duplicate script/listeners, sanitized events, blocked storage and
cross-tab changes. Run `node scripts/consent-persistence-check.cjs` for readable-stale-grant
regressions: throwing and silently ignored writes, preference reopening, no unsafe
reload, cross-tab denial, persistence recovery and tab-scoped denial across pages.
Tests do not send production analytics hits.

### Conversion paths and measurement guide (SEO-10)

The app is pre-release, so every conversion CTA is an information step to the local
`download/` page (status, app languages, what Lilora does). There are no App Store
badges, Smart App Banners or store links. Each CTA carries a fixed placement in
`data-analytics-cta`:

| Placement | Where | Destination |
| --- | --- | --- |
| `header` | Site header button, every page | `download/` |
| `footer` | Footer "get the app" link, every page | `download/` |
| `article` | App note at the end of guides, plant profiles, blog and compare pages | `download/` |
| `home-hero`, `home-closing` | Home page | `download/` |
| `download-status` | Promotion blocks linking to the status section | `download/#download-status` |
| `press-download` | Press page | `download/` |
| `page-body` | About and editorial pages | `support/` |

Events (sent only after opt-in, once per click, through the existing listener):

- `page_view`: manual, once per navigation, URL without query/fragment, blank referrer.
- `app_info_click`: a CTA to a same-origin page. Parameters: `language`, `page_path`,
  `page_type` (`home`, `guide`, `plant`, `blog`, `compare`, `download`, `support`,
  `about`, `editorial`, `press`, `<section>_index` or `other`), `cta_placement`,
  `destination_path`. No visitor text is read.
- `app_store_click`: only for the exact listing `apps.apple.com/.../id6818604360`
  on a CTA. No such link exists until launch, so it currently never fires. It is a
  click, not an install or purchase.

What GA4 can report with this setup (consented visitors only):

- Landing-page visits: `page_view` by page path / `page_type` and language.
- Information CTA click-through rate: `app_info_click` events (or users) divided by
  `page_view` events (or users) on the same pages, both from consented sessions.
  Filter by `page_type` and `cta_placement` to compare paths. Visitors who reject
  analytics appear in neither number, so the rate is a consented-sample rate, not a
  site-wide rate.
- Store click-through rate: after launch, `app_store_click` / `page_view` on the same
  basis. Installs come only from App Store Connect, not from the site.
- Acquisition source: limited. `page_referrer` is sent blank and URLs drop query
  strings, so referral sites and UTM campaigns are not recorded by this site. GA4 may
  still classify sessions from its own collection (for example the browser
  referrer on the gtag request), but this is not verified. Organic search is best
  read in Search Console and Bing Webmaster Tools. AI assistants often send no
  referrer, so AI traffic cannot be fully identified. Recording referrers or UTM
  parameters would be a collection-policy change that needs the owner's decision
  and a privacy-text update; it is not implemented.

Evidence: `scripts/consent-check.cjs` intercepts Google requests and asserts the
`app_info_click` parameter set, a single click event, no duplicate `page_view`, and
that `app_store_click` fires only for the exact listing (other App Store and external
links send nothing). Receipt in the GA4 dashboard (DebugView/Realtime) is not
verified; the owner can confirm it there after accepting analytics on lilora.app.
To report by placement or page type, register `cta_placement` and `page_type` as
event-scoped custom dimensions in GA4 Admin.
